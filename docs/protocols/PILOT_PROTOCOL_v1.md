# HydroJEV Jev 价值试点方案 v1（预注册草案）

日期：2026-09-24　状态：**待作者批准，尚未发起任何付费调用**

## 0. 要回答的唯一问题

> 在同样的证据下，Jev 能否做出确定性规则和常规模型做不到、且可测量更好的判断？

现有证据（`artifacts/hydrojev_detection_v2/`）显示答案目前是否定的：65 次真实调用中 Jev 报警概率全部在 0.84–0.95，与“≥3 个检测器报警”的规则 100% 一致；原因题 65/65 选 `insufficient_evidence`；有/无 Jev 各指标差值全为 0；测试集平衡准确率 0.608，低于 Mahalanobis 的 0.806。

诊断：(1) Jev 只在规则已判定为报警后才被调用，只能附和；(2) 传给 Jev 的 state 只有 7 个抽象分数，`hydraulic_consistency`、`observed_vs_predicted`、`attack_surface` 全为 `unavailable`，Jev 没有可供判别原因的物理信息；(3) BATADAL 没有原因标签，原因判断从未被评测。

试点针对前人方法的真实短板设计两个任务：**P1 良性误报过滤**（所有方法良性片段误报率 0.25–1.0）和 **P2 原因判别**（阈值检测器原理上做不到）。

## 1. 阶段 0：准备（不花钱）

1. 修复 `decision_primitives._require_sums_to_one`：API 概率保留两位小数，容差从 1e-3 放宽到 0.02 并加测试；否则合法实时答案会被静默替换为本地 mock。
2. 证据状态 v2（`evidence_state/2`），只用 SCADA 自身可算的量，不含标签：
   - 残差最大的 5 个通道：通道名（如 `L_T1`、`F_PU7`）、观测值、GRU 预测值、标准化残差、持续小时数；
   - 物理一致性检查（C-Town 控制逻辑可由 SCADA 自证）：泵状态与流量矛盾（`S_PU=0` 但 `F_PU>0` 或反之）；水箱液位变化方向与进出泵状态矛盾；液位是否越出训练期包络；接点压力与上游泵状态是否一致；
   - 时间上下文：小时、星期；同一时刻在训练期的典型泵状态模式及偏离程度；
   - 检测器分歧模式：哪些检测器报警、哪些没报。
3. 两个无 Jev 对照组，使用与 Jev **完全相同**的证据：
   - R1 手写规则：存在任一物理矛盾，或 ≥3 个检测器报警，则报警；
   - R2 小型监督模型：逻辑回归或浅层树，在开发集上训练，在测试集上评估（给对照组标签优势，对 Jev 更苛刻）。
4. 先用 mock 服务器干跑，生成全部请求文件；逐个扫描标签泄漏（`ATT_FLAG`、场景 ID、预期原因）和密钥，人工抽查 5 个 state 后再进入付费阶段。

## 2. P1：良性误报过滤（BATADAL，真实数据）

**设计。** 放宽候选门槛：任一检测器在 6 h 因果窗口内报警即为候选，不再要求 ≥3 个。Jev 对每个候选回答三题：
- `alarm`（noul，≥0.5 视为报警）；
- `event_type`（choice：cyber_attack / physical_fault / normal_transient / sensor_fault / insufficient_evidence）；
- `severity`（score）。

最终报警 = 候选 ∧ Jev 报警，即 Jev 拥有否决权，这正是它能产生差异的位置。

**流程。**
1. 在开发集抽 30 个候选窗口调试提问，最多两轮；
2. 冻结 state 与问题，记录哈希；
3. 跑完整开发集候选；
4. 测试集只跑一次；
5. 随机抽 20 个窗口重复调用，测一致性。

**对比对象。** Mahalanobis（现有最强）、PCA、AE、R1、R2、旧版 v2（≥3 规则）。

**指标。**
- 攻击片段召回；
- 良性片段误报率；
- 平衡准确率；
- 窗口级精确率、召回率、FPR（片段只有 7 攻击/8 良性，窗口级有数百个，用 bootstrap 95% 置信区间）；
- Jev 与 R1 的分歧率；
- 弃权率；
- 延迟、token、模型版本。

**预估调用量。** 开发集约 120 + 测试集约 60 + 调试 60 + 重复 20 ≈ **260 次**，每次约 2k 输入 token。

## 3. P2：原因判别（WNTR/EPANET 合成、带真值标签）

**场景生成**（C-Town，每类 10 个，随机化位置、幅度、起始时刻、需求噪声）：

| 类别 | 生成方式 |
|---|---|
| cyber_attack | 伪造水箱液位遥测并击穿 SCADA 联锁（复用现有 `hydraulic_mitigation` 攻击），或伪造泵状态 |
| physical_fault | `wntr add_leak` 在管段/节点注入爆管或渗漏 |
| normal_transient | 需求突增或突降、计划外但合法的泵/阀切换 |
| sensor_fault | 单传感器卡死、漂移或跳变（无物理后果） |

合计 40 个片段；另生成 200 个片段专供 R2 训练（不调用 Jev）。

**证据。** “观测 vs 正常工况数字孪生预测”的残差、第 1 节物理一致性检查、质量平衡残差（仿真可得）。

**零样本迁移测试。** 在 Net3 上按同样四类生成 24 个片段。R2 只用 C-Town 训练，Jev 不训练。这是 Jev 相对监督模型最可能的优势：无需带标签训练数据、可跨管网。

**指标。**
- macro-F1、每类召回、混淆矩阵；
- 弃权率；
- 原因概率的 Brier 分数；
- C-Town → Net3 的性能下降幅度。

**预估调用量。** C-Town 40 + Net3 24 + 调试 12 + 重复 12 ≈ **90 次**。工程量约为 P1 的两倍（需新增场景生成器）。

## 4. 预注册的通过/失败标准

**早停（P1 调试阶段即判定）。** 富证据下若 Jev 仍有 >50% 选 `insufficient_evidence`，或与 R1 在 >95% 窗口上一致，立即停止，不再花钱。

**P1 通过需同时满足：**
- 测试集攻击片段召回 ≥ 6/7；
- 良性片段误报率较 Mahalanobis（0.625）绝对降低 ≥ 0.25；
- 窗口级 FPR 的 bootstrap 置信区间优于 R1；
- 平衡准确率不低于 R2。

**P2 通过需同时满足：**
- C-Town macro-F1 ≥ 0.70，且 ≥ R1 + 0.10；
- Net3 零样本 macro-F1 ≥ R2（C-Town 训练）的 Net3 成绩。

**结论分支。**
- P1 或 P2 任一通过：论文改写为“Jev 驱动的检测与分诊方法”，以通过的任务为主结果，反射保留为后果兜底；
- 都不通过：放弃 HydroJEV-Jev 主角定位（改名或把 Jev 降为解释/分级角色），如实报告阴性结果。

## 5. 预算与安全

- 总计约 350 次调用，**硬上限 400 次**；每阶段结束汇报后再进入下一阶段。
- 每次调用使用唯一输出文件名，检查退出码；网络超时不盲目重发。
- 记录实际模型版本（当前为 `jev-1.13.0`）。
- 密钥只在子进程运行时从 Machine 环境变量读取，不写入任何文件。
- 测试集只评估一次；state 中不放任何标签或参考答案。

## 6. 已知局限（写进论文）

- BATADAL 片段数小（7/8），片段级结论只能是方向性的；
- 开发集和测试集此前在项目审计中均被查看过，不是严格意义上的“盲测”；
- P2 是仿真数据，证据中的质量平衡在真实 SCADA 中未必可得；
- Jev 是闭源服务，模型版本可能随时间变化。

## 7. 执行顺序

阶段 0（约 1 天，无调用）→ P1 调试 30 窗口（早停检查点，向作者汇报）→ P1 完整（汇报）→ P2 场景生成与调用（汇报）→ 决定论文路线。
